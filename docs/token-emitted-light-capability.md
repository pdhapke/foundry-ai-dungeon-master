# Token-emitted light source and deployment handoff

2026-10-04. Offline implementation and validation; no model requests or live light changes.

The MCP/native dirty source already contained `token.light` and `foundry_set_token_light`, but the AI DM's reviewed `sessionActionSchema` and semantic catalog omitted that action. Python's compact core tools also had no light function. Thus the DM could not discover a supported lighting action even though Foundry itself supports placed-token emission. Generic scene-token document updates exist, but expose broad document/revision machinery rather than this bounded typed capability. No campaign-specific workaround was added.

The fix extends the existing session/core protocols and mutation lanes. MCP now exposes `foundry_get_token_light` (`POST /api/session-actions/token/light/state`) with authenticated `worldId,userId,sceneId,tokenId`; the existing setter and session/core action protocols accept nonempty partial light patches. AI DM lazy discovery exposes `ai_dm_get_token_light` and `ai_dm_set_token_light`. The existing Python search/load/execute functions carry their reviewed schemas and grants; no permanent Python schema was added. Setter discovery requires the installed native lighting capability, so an old runtime does not falsely advertise support.

Read one exact placed token first, using its scene distance units. Load the setter schema, supply a stable action ID, `action:{kind:"token.light",sceneId,targetId,light:{...}}`, and exact `expectedState:{light:<observed native light>}`. Omitted light fields are preserved. `bright` and `dim` are independent absolute radii in scene units (finite 0..10000, 0.01 precision); bright-only emission with dim zero is valid. Optional color is six-digit hex or null; alpha is 0..1. Clear emission with `{bright:0,dim:0}`. This preserves tint, animation and other omitted light settings. No shield-spell distances/colors are inferred. Clarify ambiguous token selection or unspecified spell parameters. Vision/darkvision, ambient scene lights, prototype tokens and all linked actor tokens are separate scopes.

Native execution requires the exact live opted-in GM/world, active scene and placed token. It validates through the installed Token light field's clean/validate API, awaits the native Document update acknowledgement, and verifies complete preserved light state. Missing/foreign acknowledgements and changed readback cannot confirm success; existing ordering, durable receipts, deduplication and uncertainty fences remain in use. Full native light is bounded to 8 KiB before mutation and after normalization/readback; the TS targeted read/receipt transport is bounded. A discovered setter uses existing authoritative `completed` receipt plus independent readback, not direct-core one-call finalization. No deterministic single-model-call lighting completion is claimed.
