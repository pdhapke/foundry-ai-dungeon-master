# Phase 3 campaign authoring implementation plan

Read-only inspection and design, October 1, 2026. This document does not establish implemented authoring or a passed Phase 3 gate. No Phase 3 code may start before Phase 2 independently passes.

## Reuse and wiring

Retain Python's single model loop. Add fixed wrappers to the authenticated internal read adapter for `campaign_read`, `campaign_propose`, and `campaign_proposals`. `ChatKitReadTools.execute` already validates the token, binds world/user/thread, expires runs, combines cancellation signals, and rejects cross-scope callers. Route the new operations only after that validation, with bounded run calls and repeated live authorization. The server creates `WorldCampaignContext`, `ChatKitNativeActions`, and read tools in `server/src/index.ts`; use the same database connection and `authorizeChatKit` callback. `authorizeChatKit` currently checks actual world and current GM via MCP. Browser `/chatkit/actions` already authenticates, verifies current authorization, and dispatches the native action callback.

Create `server/src/chatkit/campaign-actions.ts` plus focused tests. Root owns `index.ts` and gateway wiring. Phase 2 must explicitly release `read-tools.ts` and its tests before campaign worker integration. Native actions stay untouched: root installs a routing function that dispatches campaign bodies with `kind: "campaign"` and existing native bodies to their existing owner. A legacy native-list request remains compatible; the panel makes a separate explicit campaign list request. The Python owner consumes the frozen operation shapes. Phase 5 panel owner consumes the frozen browser shapes below.

`WorldCampaignContext` is the retrieval source; refresh after approved writes, and refuse retrieval while a storage journal is outstanding. Resource authoring must match Phase 2's final metadata and overview/index contract rather than independently inventing another Markdown format. Preserve existing Izzy files; existing resources require exact hashes and reviewed edits, never implicit migration.

## Frozen candidate JSON contract for review

Model `campaign_read` arguments: `{path, startLine: 1, endLine: 80}`. Adapter injects world/user/thread. Return `{status, path, text, revision, sourceHash, span, truncated}` with a bounded excerpt. Full authoring baselines are held by the server; the model cannot select a filesystem root or an arbitrary principal.

Model `campaign_propose` arguments: `{proposalId, title, files:[{path, expectedRevision:null|string, proposedText}]}`. Strict schemas reject additional authority flags (`approved`, grant, visibility bypass, root). Bound IDs to 128 ASCII identifier characters, title to 120 characters, paths to storage's Markdown contract, files to 32, text to storage's 128 KB/file and 512 KB/new-content batch. To fit the existing 32768-byte Python adapter boundary, initially restrict conversational proposal input to 16000 UTF-8 bytes total and review response to 24000 bytes; reject oversize with an explicit split-proposal explanation, never truncate approved text.

Server-produced view: `{kind:"campaign", proposalId, schemaVersion:1, title, worldId, userId, threadId, batchDigest, expiresAt, status, requiresConfirmation:true, files:[{path, expectedRevision, beforeHash, afterHash, beforeText, proposedText, beforeCanonStatus, afterCanonStatus}], receipt, issue}`. `beforeText` and `proposedText` are the exact complete reviewed versions. A proposal must never contain hidden omitted files or sections. All hashes derive from server-read content. `batchDigest` covers schema version, scope, ordered normalized paths, expected revisions, exact before/after texts, and declared metadata transitions, using stable JSON hashing. Reusing a proposal ID with the same digest returns the existing view; different payload refuses. A new title or different file ordering is a different proposal unless canonical ordering is applied before hashing.

Model `campaign_proposals` arguments: `{}`; return the last bounded 12 entries for the authenticated scope. For large aggregate review data return summaries and explicit `reviewAvailable:false`; retrieve one exact proposal via `{proposalId}`. Approval must only be enabled for a complete exact view. Do not let list truncation become tacit approval.

Browser list body: `{kind:"campaign", threadId}`. Browser exact view body: `{kind:"campaign", threadId, proposalId}`. Browser decision body: `{kind:"campaign", threadId, proposalId, batchDigest, decision:"approve"|"reject"|"cancel"}`. The backend derives world/user from authentication, validates all fields, compares digest, and verifies active ownership, thread, expiry, and every expected revision. Browser refresh retains the digest of the exact content shown. Buttons cannot authorize a changed proposal under an old digest. Server-generated Markdown, filenames, and titles render as text, never innerHTML. Show each complete before/after file, canon promotion explicitly, and disabled approval for unavailable privacy or incomplete review.

Completed receipt: `{receiptId, proposalId, batchDigest, outcome:"completed", worldId, files:[{path, revision, sourceHash}], verifiedAt}`. `revision` and `sourceHash` equal read-back hashes. Noncompleted states have no completed receipt. The assistant may say a draft/proposal was recorded only after its persistence is verified, and canon was committed only after this receipt. Ordinary assistant prose cannot create canon or substitute for the browser decision.

## Draft and canon semantics

Initial setup collects setting, player/party, system, desired tone, safety/preferences, and a minimal starting situation conversationally. Persist drafts under `drafts/<proposalId>/...` in the same authorized world's campaign directory only after privacy passes. Draft files include `canon_status: draft`, stable IDs, revision metadata, visibility, and references. Retrieval must exclude drafts from canonical overview/narration unless specifically asked to review a draft. Proposals changing `overview.md`, `index.md`, and canonical resources include those exact versions as one batch; drafts remain separately attributable after approval.

Require the overview and index in any canonical batch that adds/removes resources or changes their identifiers/status/references. Parse and validate metadata against Phase 2's contract, require index references to resolve to existing or proposed resources, reject duplicate stable IDs and draft references from canon. Updating one resource's prose may still change the summary; default to reviewing overview/index together. Never auto-regenerate these files after approval because that would add unreviewed content. A draft-to-canon promotion is a distinct exact proposal, not an inferred acceptance of brainstorming.

## Durable states and storage prerequisite

Persist scoped entries in SQLite (`campaign_proposals` keyed by world/user/thread/proposal ID), with the immutable reviewed payload/digest, expiration, status, durable approval record, transaction ID, and receipt. Use pending → approved → dispatching → completed, plus rejected/cancelled/stale/uncertain. A conditional database update claims a dispatch exactly once, after live authorization and revision preflight; duplicates return the existing state/receipt. No approval method is reachable through model wrappers. Rejection/cancellation before dispatch has no file effect. Cancellation after dispatch requires reconciliation and cannot be represented as guaranteed rollback merely because the HTTP stream ended.

Important existing storage gap: `CampaignStorage.commit` returns verified hashes but currently removes its rollback journal without recording a durable commit ID/receipt. SQLite and filesystem commits are not one atomic transaction. A crash after files commit but before SQLite receipt save cannot be resolved safely by comparing current hashes alone; identical later content is not proof of this commit. Phase 3 must explicitly transfer storage ownership for a narrow extension: accept a server-generated transaction ID and batch digest, persist a bounded private commit marker with the receipt before deleting the rollback journal, and expose authenticated receipt lookup/reconciliation. The marker and rollback journal must share one documented recovery state machine. Startup reconciles dispatching entries: completed marker → read-back verify and save receipt; incomplete journal → authorized rollback, mark not committed; missing marker/journal after dispatch claim → uncertain, never blindly redispatch. Durable markers need bounded retention tied to SQLite references; do not quietly delete referenced receipts.

Do not imitate native actions' blanket restart-to-uncertain handling when stronger filesystem evidence exists, and do not claim the current storage already has durable receipts. Preserve native dice/private-note behavior. Serialize campaign browser commits with ordinary/event turns using the existing per-world turn serialization, or an explicitly shared world queue; `/actions` currently bypasses `ChatKitTurns.enter`, so storage's file lock alone does not serialize narration with edits.

Storage authorization is synchronous, while live Foundry authorization is asynchronous. The adapter must revalidate live authorization immediately before a synchronous storage operation and supply a short-lived operation lease whose callback checks the same immutable identity/world, cancellation, expiry, and current run capability. Revalidate again before publishing the result. Do not describe a cached identity boolean as fresh network revocation checking. The synchronous batch blocks the JS event loop, so revocation timing limitations must be acknowledged and tested at the lease boundaries.

## Privacy and current deployment

All private persistence, including draft files, proposal payloads, journals, staging files, and receipts, requires a verified private serving boundary. Current configuration remains unchanged. `CampaignStorage` defaults to denying private writes; no browser/model argument can lift that gate. Production proposal persistence and canon commit return `storage_unavailable` with an actionable privacy reason until deployment verification is approved and performed. Avoid storing new sensitive drafts in another statically served database as a workaround. Offline fixtures construct storage using an isolated temporary root and an explicit fixture-only privacy callback; that does not prove live privacy. Existing campaign reads are preserved within their authorization/visibility policy without asserting they are publicly protected.

## Independent acceptance evidence required

Use real temporary filesystem plus real SQLite to test propose → exact view → authenticated approve → persisted receipt → later retrieval; include a fake-model scripted conversation and label it a contract fixture. Assert prose-only approval cannot commit. Cover duplicate and conflicting IDs/digests, stale expected revisions, index inconsistency, cross-world/user/thread requests, expired authorization, privacy denial, cancellation at every state, restart before claim/after claim/during file writes/after marker/before SQLite receipt, journal recovery, uncertain dispatch, and unchanged legacy Izzy resources. Check injection strings are rendered/handled as data. Verify typed and application-triggered turns see refreshed overview only after a completed canonical receipt. Independent validator reports PASS/FAIL/BLOCKED before Phase 4 starts. Real model conversation, loaded Foundry behavior, and direct-file privacy remain separate live gates requiring explicit authorization and budget.
