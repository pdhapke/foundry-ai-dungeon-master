# Prompt 1 reusable context preparation

Offline implementation, 2026-10-03. No inference, runtime restart, player enrollment, world mutation, automatic event changes or paid service used.

`ChatKitReadTools.prepare` authorizes current GM identity before and after preparation. It warms the existing `WorldCampaignContext.overview` source-hash/parser owner and existing trusted MCP catalog, concurrently. It returns only readiness metadata; campaign text remains server-side. Base instructions and core schemas remain owned by the Python context assembler rather than duplicated in a Node content store.

Catalog preparation shares one operation for an identical world/user/client/lane/GM/configuration/connection scope. Cache entries and pending operations are capped at 32; refresh has a ten-second bound. Copies isolate caller mutation. Logout/disconnect/reconnect invalidation clears metadata and fences delayed publication. Gateway owns invoking invalidation. Configuration scope is passed by gateway; incompatible server builds naturally begin with an empty process-local cache.

The MCP supported slice exposes `listTools` and `callTool`, with no dependable change-event sequence or inexpensive remote revision probe. Catalog metadata therefore expires after a conservative 15 seconds, with no periodic refresh loop. A different already-published catalog digest invalidates reused metadata. The small campaign overview is source-loaded/hashed and access-filtered every command using the pre-existing parser cache. Campaign edits, locks and invalid metadata therefore do not reuse an old content snapshot. No second campaign storage/cache was introduced.

Live world, system, scene and combat are still read on each initial context; actor/detail reads remain on demand. Parallel independent reads and dependent final authorization are preserved. This is a consistent bounded observation, not an atomic Foundry transaction; detailed action validation remains authoritative. No reliable scene/combat event sequence was found on this adapter, so no stale live state cache was added. Prepared capability metadata never grants execution authorization. Authenticated MCP and current GM checks remain mandatory.

Preparation telemetry records context duration, catalog hit/miss, invalidation reason, age and revision. Existing command spans continue to record residual source hashing, authorization and live reads. A successful warmup moves catalog fetch/parsing before submission, and avoids it while valid; source checks and live reads are deliberately residual work. No idle background polling overhead is introduced. Timing is offline fixture evidence, not a live latency claim.

Validation: server `npm run typecheck` passes. `prepared-context.test.ts` plus existing `read-tools.test.ts`: 12 passed; `prepared-context.integration.test.ts`: 1 passed. Integration evidence in `prompt1-context-tests.log` demonstrates two concurrent preparations fetch one catalog, two commands fetch no additional catalog and receive different freshly read scenes, current revocation rejects, reconnect refreshes, and non-GM preparation rejects. Cache tests cover identity/revision separation, bounded age, delayed publication after invalidation, cancellation isolation and failed-work recovery. Independent review is owned by the parent validation worker.

Limitations: preparing checks prerequisites but cannot promise a later provider request succeeds. Positive live player perception acceptance still requires reconnect/enrollment; existing accepted sentence is only "A section of corridor floor is visible here." at one native-visible Sargauth point. This change neither broadens that secrecy/narration gate nor supplies NPC detection/trap/round/map capabilities. Runtime/browser loaded configuration validation remains pending manual server restart and parent-supervised inspection.
