# World campaign storage: offline MVP

`CampaignStorage` takes a trusted server-configured worlds directory, plus a live capability revalidation callback. It resolves `<world>/data/campaign` itself. Browser/model callers supply only a world identifier and relative Markdown resource names. The callback must bind the caller to the live authorized world; it is checked before access and during each batch. The existing Izzy campaign and deployment settings are untouched.

Private writes fail closed unless the server supplies `assertPrivateStorage`. That callback is a deployment gate, never a browser flag. No production adapter is enabled in this phase. Foundry's unauthenticated static Data serving was independently observed; companion authentication cannot protect those URLs. A supported deployment must enforce authentication and world/user authorization on every campaign-file request through a supported serving configuration or authorized gateway, with origin bypass closed. The implementation does not assume such a configuration exists, alter Foundry vendor code, or use obscure paths as protection. Direct HTTP privacy verification and approval of any server/network changes remain required before enabling live private writes.

Reads and writes are bounded (128 KB/file, 512 KB/new-content batch, 32 files). Prior snapshots are independently bounded at 32 files × 128 KB. JSON journals account for sixfold control-byte escaping, bounded identifiers, and structural overhead: the default maximum is 24,617,776 bytes. The identical serialized limit is enforced before commit and before recovery reads; constructor budgets are restricted to positive integers no larger than 1 MiB/file and 32 MiB/new-content batch. Only normalized relative Markdown names are accepted; traversal, Windows streams, reserved names, symbolic links/junctions, and world-directory escapes are rejected. Revisions are SHA-256 of exact UTF-8 content. Batches require each expected revision (null means absent). Receipts follow read-back verification. Parent directories are created safely beneath an existing authorized world.

A filesystem lock serializes cooperative writers, including separate repository instances. Each batch first persists a fsynced rollback journal, then atomically replaces individual files. Readers refuse incomplete transactions. `recover(worldId)` restores the prior snapshot and can be rerun after another interruption. This is recoverable multi-file consistency, not an OS-level simultaneous multi-file rename. A crash leaving `.write-lock` requires an operator to confirm its writer process stopped before removing that lock; automatic stale-lock theft could corrupt an active transaction. Journal/staging artifacts may contain private text and need the same serving protection as Markdown.

Scope limitations: Node lacks Windows openat-style handle-relative traversal, so local administrators or noncooperative filesystem writers must not alter directories during operations. The lock protects repository users, not hostile local administrators. fsync of files is used; power-loss durability of directory entries depends on the platform. A crash before journal rename can leave `.transaction.json.pending`; recovery of that precommit staging artifact requires operator inspection/removal and does not imply any resource was committed. Commits are revision checked, but durable conversational proposal/idempotency receipts belong to the next adapter layer.

Evidence: five focused tests operate on real temporary directories/files, including a Windows junction, concurrent writer lock rejection, bounded content and names, revision conflict, cross-world authorization, revoked access, mid-batch revocation, restart rollback, malformed recovery world, interrupted staging rename, and default private-write denial. Server TypeScript checking passed. These are deterministic storage tests; they do not prove live Foundry privacy or model behavior.
