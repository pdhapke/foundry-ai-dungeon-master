# Solo DM pause latency: source analysis

Read-only source audit, 2026-10-01. No model requests, live mutations, configuration changes, or benchmarks were performed. Counts describe the normal successful changed-state path, not measured elapsed time. No AGENTS.md was found beneath the workspace.

## Main finding

The actual pause mutation is surrounded by many network calls, and the response is gated on more network calls for every streamed chunk. Model reasoning is only one possible contributor. The implementation has enough redundant serial work to plausibly explain a very slow successful pause/unpause, but timings are required to attribute the reported delay.

## Evidence and call accounting

- `server/src/index.ts:157`: every `authorizeChatKit` performs three MCP calls in parallel: current world, user by ID, user active status. Each authorization therefore costs one serial network group and three requests. World equality, current GM role, active user, and identity equality are validated each time.
- `server/src/chatkit/gateway.ts:112,165,228`: normal ingress checks authorization, checks again after entering the ordered turn, then checks before forwarding every upstream stream chunk. For C chunks, forwarding alone adds C authorization groups / 3C MCP requests. Chunks are transport chunks, not meaningful security events. The next reader read waits for the preceding authorization and response write. This can delay visible output even after the mutation completed.
- `chatkit-server/app.py:248`: every response first awaits the full authorized `context` snapshot before starting `Runner.run_streamed`. A simple pause request pays the same context cost as story/rules questions.
- `server/src/chatkit/read-tools.ts:249-470`: with campaign enabled and an active scene, context performs world, scene list, scene, system, combat, then N party actors serially, where N <=16 counts inspected actor candidates, which may differ from returned party members. There is one authorization at start, one before and after each state read, and one at end. Therefore context costs **5+N state calls, 12+2N authorization groups, and one tools/list**, or **41+7N MCP tool calls plus one list**. With four party actors: 69 tool calls and one list, before the first model request. Without campaign, the baseline differs; without active scene scene-specific reads are skipped, but assigned-party inspection can still occur. Actors are explicitly awaited in a for-loop.
- `server/src/chatkit/catalog-tools.ts:445`: every search/load/execute authorizes, refreshes its catalog (a real tools/list via provider snapshot), then authorizes at return. `server/src/tool-catalog/runtime.ts:245` refreshes again inside executeGrant. Thus an execute pays two catalog refreshes before adapter-specific refreshes. `server/src/integrations/foundry-local-api-mcp.ts:26` forwards listTools to the MCP SDK without an application cache.
- `chatkit-server/dm_prompt.py:16`: pause instructions require search, load the read and setter schemas, read state, then execute setter. Those dependencies require at least search -> loads -> read -> setter -> final model responses (five model requests if loads share one model step), or six if loads are selected separately. There are five Python-to-Node tool requests (search, two loads, read execution, setter execution). Additional tool/model decisions can increase this.
- `server/src/chatkit/pause-actions.ts:read`: pause read adds authorization, listTools, state call, authorization. A discovery-granted pause read therefore costs six authorization groups, three tools/list calls, one state call.
- `server/src/chatkit/pause-actions.ts:request`: changed-state setter adds eight authorization groups, two tools/list calls, and four state calls: initial read, immediate pre-dispatch re-read, explicit setter, post-read. Discovery session authorization adds two groups, and catalog entry/invoke/return adds four more. Therefore the setter execution costs **14 authorization groups, four lists, four state calls**. No-op state-already-desired path exits mutation logic and is cheaper.

For the common prescribed search + two loads + read + changed-state setter path, discovery/action work totals **26 authorization groups (78 auth MCP calls), ten tools/list calls, five pause state calls**, before gateway checks and initial context. Search and each load cost two authorization groups and one list. With active campaign and N party actors, total base work across the turn is approximately **130+7N MCP tool calls plus 11 lists**, counting two gateway ingress authorizations, and then **3C more auth MCP calls** for C streamed chunks. With N=4 this is 158 tool calls plus 11 lists, plus streaming overhead. This is a source count, not a claim that the transport executes each individual request serially: the three auth reads within each group are parallel.

## Limits and secondary contributors

Python `read_foundry` creates a fresh httpx AsyncClient for every adapter request (`app.py:123`), preventing reuse of that client's connection pool. Its httpx timeout is12 seconds per phase/inactivity, not a hard total wall-clock deadline. Node read/discovery/native operations usually have a shared 10-second abort deadline; these do not mean every nested step can consume ten seconds independently. Gateway has a default five-minute run timeout. `Runner` has max_turns=8 and OpenAI retries disabled. Discovery budgets are four searches, six loaded definitions, twelve executions, with an adapter cap of 22 discovery operations; individual native/general reads share run.calls <=12. Search/load grants are scoped to a response, so a later pause request repeats discovery.

The Python SQLite methods are synchronous inside async methods, load all thread items before taking the recent page, and commit individual writes. Long chats or concurrent work could block the event loop; this is a secondary source hypothesis, not evidence of the reported delay. One Runner loop is used; there is no visible multi-agent handoff in this Python path. Ordered-turn gates intentionally prevent competing turns; queue wait should be measured separately from execution time.

## Proposed improvements, in priority order

1. **Measure first:** record correlation-based durations for turn queue, initial context, each authorization group, each tools/list, model request/first token, pause dispatch/readback, and stream forwarding. Record counts and timings, never credentials or raw campaign text. This distinguishes execution delay from UI delay.
2. **Make revocation checks atomic and cheaper:** add a provider-side authorized world/user/active-status snapshot returning all three checks in one coherent call. Retain checks at response release and immediately before mutation. Avoid replacing them with a long-lived TTL cache. A push revocation/world-change epoch can support immediate abort; if stream chunks stop doing live checks, define and test the revocation guarantee explicitly. A safe incremental change is coalescing simultaneous in-flight checks only when their captured authorization epoch and scope agree; never reuse checks begun before a revocation event.
3. **Remove duplicate same-boundary catalog refresh:** let executeGrant consume the just-validated immutable snapshot from catalog execute, rather than immediately listing again. Preserve catalog revision, policy revision, grant expiry, world/run scope, and selected input/upstream schema digest checks. Search and loads can use a response snapshot, with mandatory freshness/drift verification at execution. Selected pause dependencies can be checked without recomputing every facade definition if provider supports atomic schema revision/etag. Invalidation on tools/list_changed/reconnect must clear caches. A plain TTL cache alone weakens drift detection.
4. **Skip irrelevant initial context for deterministic game control:** when the trusted ingress parser recognizes an explicit pause/resume desired state, provide minimal current-world/action context and pause state, rather than reading scene, system, combat, and up to sixteen actors. Do not infer intent from model arguments, history, campaign files, or automatic observations. General DM requests retain full context. Independent system/combat/actor reads can also be bounded-parallel after validating scene/world, with authorization rechecked before releasing the combined projection.
5. **Collapse model decisions for simple commands:** use a deterministic reviewed pause endpoint or run-scoped preloaded pause read/set grants for explicit ingress-parsed intent. This can eliminate several sequential model roundtrips, while preserving exact schemas and allowed effect. Desired state must be explicit, never toggle. Retain stable actionId, durable insert-only claim, argument-conflict rejection, preconditions, immediate pre-dispatch authorization/schema/state verification, post-read, and uncertain/cancelled receipt semantics. Never automatically redispatch an uncertain action.
6. **Reuse Python HTTP pool and bound storage reads:** lifespan-managed adapter client with per-request deadlines; SQL LIMIT/cursor queries rather than materializing all items. Keep owner/world/thread checks and complete-message context budgeting intact.

## Preservation requirements

Do not trade speed for current GM/world/active-user checks, revocation at dispatch/release, upstream schema drift detection, run-bound grants, cancellation, ordered turns, exact argument validation, durable idempotency, or authoritative post-read. Any changed authorization freshness semantics need explicit documented guarantees and tests. The existing double state read around claim narrows a concurrency window; remove it only if the Foundry provider offers an atomic expected-state setter that supplies equivalent protection.
