## Actual path and existing boundaries

1. `module/src/ai-dungeon-master/chatkit-context.ts:73` requires a GM; its allowlist limits client hints to scene/combat/controlled/target IDs and scene name. Hints are explicitly untrusted, but GM-selected hidden IDs and private scene names can still be present.
2. `chatkit-server/app.py:963` authenticates a gateway GM principal. SQLite owner is `[worldId,userId]` (`:46`), not an intended player or disclosure audience. Existing chat is GM-owned; this is not a player-access authentication bug, but its prose has no strict player-safe guarantee.
3. Python `foundry_read_token_perception` (`:806`) calls `read_foundry` (`:125`) over loopback `/internal/chatkit/read`, using Node-issued run capability and world/user/thread headers. No fallback credentials or GM native visibility is requested by that tool.
4. `server/src/chatkit/read-tools.ts:313` authorizes the GM run, selects catalog tool `foundry_get_token_visibility`, dispatches selected scene/token/effective user, and reauthorizes the GM run after asynchronous response. The native MCP endpoint/client is a separate identity gate. Projection (`player-perception.ts`) checks exact selected/world observation identities, non-GM opt-in, ownership flags, revision consistency, render flags, complete isolation/environment and truncation. The projector allowlists fields and discards issue text/hidden counts/barrier coordinates/secret door metadata. This is a sound bounded tool-result boundary, not a whole-narration boundary.
5. Python returns projected JSON directly as a tool result. `PauseTimingHooks.on_tool_end` (`app.py:598`) durably writes complete call/result pairs as `authoritative_tool_exchange_v1` in a `HiddenContextItem`. `ReceiptHistoryConverter` (`:278`) restores those complete pairs verbatim into model input on reconnect.
6. `FoundryChatKit.respond` (`:854`) loads the last 20 GM thread items, converts them, bounds context while preserving adjacent complete pairs, appends `initial_context`, and runs the same `build_agent`/DM_PROMPT. `stream_agent_response` streams model prose into that same thread. No distinct player narrator or output fact validator exists here.

## Minimal compatible repair plan

Prefer deterministic player factual projection/receipts first. Keep GM adjudication and native mechanics intact. Add an explicit player output lane, never infer it from a model-authored label or quoted user data. Bind a trusted server-issued audience to world, intended player, selected token/client, consent/ownership revision, thread and observation revision. Do not silently turn every existing GM chat into a player thread.

Use existing `AiDmVisibility`, `AiDmAccessScope`, `AiDmFact`, context access/declassification policies and campaign section parser rather than a second campaign store. Introduce a strict allowlisted `PlayerObservableResultV1` at the adapter seam: version, opaque receipt/observation handle, audience/world binding, readiness (`ready`, `not-connected`, `unsupported`, `stale`), approved facts and approved results. Each fact has a kind (`area-observed`, `entity-noticed`, `revealed-description`, `approved-mechanical-result`), safe text or typed values, disclosure decision and server-backed provenance. Public output must omit secret IDs/labels, raw coordinates/private rationale, internal source labels/URIs, counts of excluded entities and diagnostic free text. Keep internal provenance mapping private; only safe opaque reference crosses the boundary. Never infer creature noticing the player or a trap firing from visibility alone.

Split storage explicitly: existing GM-owned SQLite history/private adjudication remains full complete call/result pairs; a player-visible items table/store or distinct audience-owned thread contains only projected facts, approved receipts and validated narration. Preserve pair integrity inside each correctly authorized lane. Never copy a raw private pair into player history for SDK protocol continuity. Player reconstruction must reject legacy unclassified GM items and histories; migrate by creating an empty safe lane, not by summarizing private transcripts with an unrestricted model.

The strict narrator (only when explicitly requested/approved) receives solely validated contract, safe user request, audience-approved campaign descriptions and safe history. No GM snapshot, raw retrieval, private transcript, original errors, raw action receipt or unrestricted tool catalog. Tools disabled. A second model pass adds latency/usage and needs budget disclosure; routine projected receipts add no inference. If existing GM model still writes final player prose, report the weaker policy-only guarantee.

Before accepting asynchronous perception/narration, recheck current intended player/client/non-GM/opt-in/ownership/world and revision. On changed world/player/consent or invalidated observation, withhold result with safe stale code. Historical approved mechanics may be preserved as historical receipt, but must not authorize a new mutation or reveal present facts. Publication guard should bind a monotonically changing audience/state generation and cancellation token, not just a timestamp. Existing narrow permanent mutation revocation must remain intact.

## Required adversarial model-free gate

Sentinel secrets in hidden creature/trap/secret door name, coordinates and auxiliary fields; private journal/notes and source URIs; historical user/assistant/tool pairs; malformed/incomplete perception; retrieval instruction injection; GM discovery errors; stale parsed cache and source changes; reconnect + history reconstruction; player/world/consent/ownership changes while result pending; confirmed private HP receipt; explicit authorized reveal. These tests prove structural privacy, not model narration quality or native browser rendering.
